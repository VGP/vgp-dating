# treePL testing ground

This folder is just for running tests using [treePL](https://github.com/blackrim/treePL) to see how the tree responds to different constraints. Here is an example with the current [constraints](/calibrations/calibrations.md):

![treePL constraints test](roadies_v1.1.16b/generated/roadies_v1.1.16b.treePL.png)

Shared input trees and annotations are stored in `../trees/`. Configurations and results for each analysis are kept in its own folder, currently `roadies_v1.1.16b/`. All analysis outputs are kept in `generated/` beneath the configuration directory, including benchmark and replicate results, logs, dated trees, plots, and age reports. Configurations and the launcher stay outside this folder. The launcher recreates `generated/` when needed; it does not delete existing results automatically.

Run the ROADIES launcher with `bash treePL/roadies_v1.1.16b/roadies_v1.1.16b.sh` from the repository root. It benchmarks settings and updates the final configuration with the recommended smooth, opt, optad, optcvad, pliter, and plsimaniter values, plus the moredetail, moredetailad, and moredetailcvad flags. It then runs 200 replicates with random seeds, records the selected seed in the final configuration, and runs that configuration once more to produce the standard result tree and final log. The lowest-objective replicate remains saved separately. Missing or incomplete recommendations stop the launcher. These configuration updates use Python 3; calibration constraints are not changed. The launcher finishes by running `roadies_v1.1.16b.treePL.R` from `treePL/`, generating the plot, scientific-name tree, and calibrated-node age table. Plotting output is saved in `generated/plotting.log`; a plotting failure stops the launcher with `stage=plotting`, and the workflow is marked complete only after plotting succeeds. Plotting requires the rphylopic, phytools, plotrix, and png R packages and internet access for silhouettes. To rerun plotting alone, use `Rscript roadies_v1.1.16b.treePL.R` from `treePL/`. Existing results have been moved without rerunning the analysis.

The default fast benchmark starts with adaptive prime searching, then uses one recorded seed for initial PL convergence with a buffer and full leave-one-out CV. Screening uses eight decade-spaced values from 100 through 0.00001. All three CV stages use the initial benchmark's recommended pliter and plsimaniter, with cviter=3 and cvsimaniter=5000, and omit `thorough`. PL convergence checks and production runs retain `thorough`. The default seed is 1729; random seed mode generates and records one seed. The separate thorough profile retains its existing multiple-seed random-CV tuning and full-CV validation.

Refinement restarts between the coarse winner’s immediate neighbors with five half-decade values. A third sweep restarts between the refinement winner’s immediate neighbors with five quarter-decade values. For example, a coarse winner of 1 gives a second grid of 10, 3.16228, 1, 0.316228, and 0.1; if that selects 3.16228, the third grid is 10, 5.62341, 3.16228, 1.77828, and 1. The three sweeps evaluate 8 + 5 + 5 values before any boundary extensions. Each sweep selects using only its own scores. Overlapping scores are reported to reveal restart sensitivity; no score-change threshold or convergence guarantee is imposed. Final PL convergence is checked at the third sweep’s selected smoothing before the configuration is updated.

Fast mode does not perform an independent seed check; its final recommendation records `cv_method=full` and `cv_seed_check=not_performed`. The later 200 production replicates explore optimization at the chosen settings; they do not re-evaluate smoothing.

A boundary winner extends the grid by two values in that direction and reruns the entire continuous descending grid. Earlier points are retained. Scores from different attempts are not pooled. Each stage permits up to six extensions before stopping without a recommendation. Grid positions define candidates independently of rounded treePL output. An exact score tie is ordered toward higher smoothing; a boundary winner still requires expansion. There is no wall-time cutoff, and duration depends on optimization and extensions.

Fast-mode score tables are `full_cv_screen_scores.tsv`, `full_cv_refine_scores.tsv`, and `full_cv_fine_scores.tsv`; the latter two stages have matching `_summary.tsv` timing tables and `_overlap.tsv` comparisons against the preceding sweep. Overlap tables report signed percentage score changes; a zero previous score with a nonzero current score is marked `NA`. The second sweep saves `full_cv_refine_recommendation.txt`; only the third supplies the final smoothing recommendation. Attempt grids, scores, configurations, and logs are retained in `generated/treepl_parameter_benchmark/screen_cv_attempts_*`, `refine_cv_attempts_*`, and `fine_cv_attempts_*`. Grid indices use quarter-decade units (`smoothing = 10^(index/4)`). Each attempt records its winning grid index and percentage gap to the runner-up in `decision.tsv`. Invalid, nonfinite, duplicate, or missing candidate scores stop the fast search. Stopping boundaries include a small numerical margin so rounding does not omit the intended last grid value. Failed CV processes also retain score counts and exit status in `failed_cv_*` directories. Prime trial seeds are explicit and recorded in `prime_seeds.tsv`.

Prime selection parses the three optimizer numbers and three optional flags by name and keeps their complete combination together. Both profiles use adaptive prime searching: at least 40 successful trials, up to 200 launched trials, and two concurrent processes by default. Trial seeds are distinct and recorded. Every ten successful trials, early stopping checks whether the leading combination has at least 25% support, a 10-percentage-point lead, and the same leading combination across three consecutive checkpoints; otherwise the search continues to its maximum. The most frequent complete combination is selected. Omitted flags are recorded explicitly as 0; recommended flags are recorded as 1. The selected flags apply throughout PL and CV benchmarking and are enabled or commented out in the final configuration before replicates run. Old active flags are removed when no longer recommended. Invalid prime recommendation blocks are excluded, with their logs retained in `failed_prime_*`.

Replicate selection requires a finite numeric objective and reports attempted, successful, and failed counts in `replicate_counts.txt` and the selection record. Failed attempts are excluded; the best successful replicate is retained even if some attempts fail. Previous selection artifacts are cleared at the start of a rerun.

After updating the selected seed, the launcher saves `generated/roadies_v1.1.16b.final.config` and runs that snapshot from the analysis directory, so its relative paths retain their meaning. Final validation requires R with the ape package: the output must parse as a tree with finite, nonnegative branch lengths and the same taxa as the input. A finite final objective is also required. `generated/final_run_status.txt` distinguishes a running or failed workflow from a validated completed analysis and records both final and selected-replicate objectives plus replicate counts. The previous final tree is removed just before the final run to prevent stale output from passing validation.

Fast CV prints the stage, grid range, seed position, every completed smoothing value and score, and elapsed time. While a value is running, it prints a heartbeat every two minutes with the completed-value count and the latest available optimization/CV activity. Full-CV heartbeats also report approximate completed leave-outs and a percentage for the current smoothing value, using the input tree’s tip count. Counts reset for each value and may lag or undercount because parallel log output can be buffered or interleaved; the saved CV score remains the completion check. If R/ape cannot supply the tip count, the heartbeat reports a count without a percentage. Full process logs remain saved with each attempt. These progress messages are activity reports, not runtime estimates.
